# Feature Requirements Document: Руководство по созданию FR

Версия: 1.0
Дата создания: 2025-10-31
Тип документа: Инструкция и шаблон для создания FR (Feature Requirements)
Область применения: Доработка и расширение существующих систем

---

# Что такое Feature Requirements

Feature Requirements (FR) - это документ, описывающий требования для добавления новой функциональности или существенной доработки в существующую систему. В отличие от PRD (Product Requirements Document), который создаётся для нового проекта с нулевой точки, FR создаётся в контексте уже работающей архитектуры, технического стека и пользовательской базы.

# Критические принципы работы с FR

## Принцип №1: Контекст существующей системы

FR создаётся НА ОСНОВЕ анализа существующего кода, архитектуры, баз данных и паттернов. Каждое требование должно быть согласовано с текущей реальностью, а не с идеальным состоянием системы.

## Принцип №2: Полнота и однозначность

Если любая информация неясна, неполна или допускает множественные интерпретации - вы ОБЯЗАНЫ остановиться и задать уточняющий вопрос ДО заполнения соответствующей секции FR. FR содержит ВСЮ необходимую информацию для работы, но только информацию, которая добавляется или изменяется.

## Принцип №3: Минимальность при полноте

FR должна быть лаконична, но содержать все необходимое. Не дублируйте информацию из существующих документов (архитектура, технический стек) если они не изменяются. Сосредоточьтесь на изменениях и новых требованиях.

## Принцип №4: Трассируемость к коду

Каждое требование в FR должно быть связано с конкретными местами в коде: названиями модулей, файлами, существующими функциями, которые нужно модифицировать или расширить.

# Процесс создания FR: пять этапов

## ЭТАП 1: Анализ текущего состояния системы

Ваша задача - провести систематический аудит существующего кода и документации.

### Задача 1.1: Извлечение артефактов проекта

Проанализируйте следующие документы и файлы:

# Документация
- README.md и другие документы в корне проекта
- ARCHITECTURE.md если существует
- Существующие PRD.md или FR-*.md файлы
- API документация (Swagger/OpenAPI specs)
- CHANGELOG.md

# Конфигурационные файлы
- Корневые файлы проекта (package.json, go.mod, requirements.txt, Cargo.toml)
- Environment конфигурации (.env.example, docker-compose.yml)
- Конфигурации для CI/CD (.github/workflows, .gitlab-ci.yml)

# Структура кода
- Организация модулей и функций
- Текущие точки входа и API endpoints
- Схемы баз данных и миграции
- Типы данных и interfaces

# Специальные маркеры в коде
- Комментарии TODO, FIXME, HACK, DEPRECATED
- Версионирование и метаданные
- Known limitations и workarounds

### Задача 1.2: Определение текущей архитектуры

Для каждого основного модуля систем документируйте:

# Компонентная архитектура
- Название компонента и его ответственность
- Основные файлы, которые реализуют компонент
- Зависимости от других компонентов
- Текущие API (функции, endpoints, эвенты)

# Паттерны взаимодействия
- Как компоненты взаимодействуют друг с другом
- Асинхронные vs синхронные вызовы
- Message flows и event handling
- Механизмы обработки ошибок

# Хранение данных
- Какие сущности хранятся и где
- Связи между сущностями
- Текущие индексы и оптимизации
- Механизмы для масштабирования

### Задача 1.3: Выявление ограничений и constraints

Определите КРИТИЧЕСКИЕ ограничения существующей системы:

# Технические ограничения
- Версии языков и фреймворков
- Поддерживаемые браузеры и платформы
- Известные limitations в текущем коде
- Technical debt и его влияние на новые функции

# Архитектурные ограничения
- Количество параллельных пользователей
- Объёмы данных, которые может обработать
- Процессы, работающие в реальном времени vs батч-процессы
- Интеграции с внешними системами и их constraints

# Бизнес-ограничения
- Версионирование API (backward compatibility требования)
- Compliance и regulatory требования
- SLA/SLO на производительность и доступность
- Расписание обслуживания и downtime

### Контрольные вопросы для Этапа 1

Если вы НЕ можете однозначно ответить на эти вопросы, задайте критический вопрос пользователю:

# Фундаментальные вопросы
- Какие основные модули существуют и что они делают?
- Какова текущая архитектура (монолит, микросервисы, гибридная)?
- Какие API endpoints существуют?
- Какие сущности хранятся и как?

# Вопросы о ограничениях
- Какие текущие limitations системы критичны для новой функции?
- Есть ли known issues, которые нужно учесть при разработке?
- Какие части кода нестабильны или требуют особой осторожности?

# Вопросы о зависимостях
- От каких внешних сервисов зависит система?
- Какие compliance требования действуют?
- Какие версионирования constraints на API?

## ЭТАП 2: Интервью с пользователем для выявления требования

Проведите структурированное интервью, состоящее из 5 основных этапов. После каждого этапа резюмируйте информацию и уточняйте детали.

### ЭТАП 2.1: Описание желаемого изменения

Цель: Понять, ЧТО именно нужно добавить или изменить в системе и ПОЧЕМУ

# Ключевые вопросы
- Опишите желаемую новую функциональность или изменение существующей функции
- Какую проблему решает эта доработка? Какая боль/неудобство текущего состояния?
- Кто будет использовать эту новую функциональность? (пользователи, администраторы, другие системы)
- Почему эта функциональность нужна именно сейчас? Есть ли жесткие сроки?
- Как это связано с текущей бизнес-стратегией?

# Критерии достаточности информации
- Четко сформулирована суть изменения в 1-2 предложениях
- Известна целевая аудитория этого изменения
- Понятна бизнес-ценность изменения
- Известны текущие болезненные точки
- Определены основные успешные результаты

### ЭТАП 2.2: Анализ взаимодействия с текущей системой

Цель: Понять, как новая функция будет интегрироваться с существующей архитектурой

# Ключевые вопросы
- Какие существующие компоненты системы будут затронуты?
- Какие существующие данные нужно использовать или изменить?
- Нужно ли создавать новые сущности данных или достаточно изменить существующие?
- Как пользователи будут взаимодействовать с новой функцией? (через UI, API, интеграция)
- Какие текущие workflows станут другими из-за этого изменения?
- Нужна ли миграция существующих данных?

# Критерии достаточности
- Определены все затронутые компоненты системы
- Известны зависимости между компонентами
- Понятна карта потоков данных
- Выявлены потенциальные конфликты или сложности
- Определены критичные пути интеграции

### ЭТАП 2.3: Технические требования и constraints

Цель: Выявить технические ограничения, которые повлияют на реализацию

# Ключевые вопросы
- Есть ли специфичные требования к производительности? (время отклика, throughput)
- Нужна ли специальная безопасность/авторизация для новой функции?
- Должна ли функция работать в определенных условиях (offline, с ограниченным интернетом)?
- Какова целевая платформа/браузер для этой функции? (Отличается ли от текущей?)
- Есть ли требования к совместимости с существующим code (backward compatibility)?
- Какие версии dependencies НЕЛЬЗЯ менять?
- Нужна ли поддержка для старых данных или версий API?

# Критерии достаточности
- Определены все non-functional requirements
- Известны constraints от существующей системы
- Понятны требования к backward compatibility
- Выявлены потенциальные конфликты с текущими ограничениями
- Определены constraints для development (нельзя менять API версию, СУБД, etc)

### ЭТАП 2.4: Пользовательские сценарии

Цель: Детализировать основные способы использования новой функции

# Ключевые вопросы
- Опишите типичный сценарий использования новой функции от начала до конца
- Какие шаги делает пользователь?
- Какие данные пользователь вводит и какие получает в результате?
- Есть ли альтернативные пути выполнения одной и той же функции?
- Что происходит при ошибках? (error handling, recovery)
- Какие подтверждения/валидации нужны? (особенно для опасных операций)
- Какие уведомления должны получить пользователи? (успех, ошибки, асинхронные обновления)
- Как новая функция будет взаимодействовать с существующими features?

# Критерии достаточности
- Описаны 2-4 основных user flows
- Каждый flow детализирован пошагово (8-15 шагов)
- Определены точки принятия решений
- Выявлены edge cases и исключительные ситуации
- Понятны input/output данные

### ЭТАП 2.5: Бизнес-контекст и метрики

Цель: Понять бизнес-цели и как будет измеряться успех

# Ключевые вопросы
- Какие метрики успеха для этого изменения? (adoption, engagement, revenue, cost savings)
- Какая целевая аудитория? (какой % пользователей это будет использовать)
- Какой timeline для реализации? Есть ли жесткие дедлайны?
- Какой budget? Есть ли ограничения на инфраструктуру?
- Кто решает о приоритете этого изменения?
- Будет ли это экспериментом (A/B test) или full rollout?
- Какие риски нужно миттигировать?
- Как это влияет на roadmap на 6-12 месяцев?

# Критерии достаточности
- Определены измеримые метрики успеха
- Известен timeline реализации
- Понятны приоритеты и решающие факторы
- Выявлены основные риски
- Определена стратегия rollout

### Итеративный процесс уточнения (Этап 2)

После каждого подэтапа интервью обязательно:

# Шаг 1: Резюмируйте информацию
- Ключевые инсайты из ответов
- Что вы поняли о требовании
- Какие детали выявились

# Шаг 2: Выявите gaps
- Какая информация все еще неясна
- Какие противоречия обнаружены
- Какие assumptions нужно проверить

# Шаг 3: Задайте уточняющие вопросы
- Для каждого gap - конкретные вопросы
- Проверьте assumptions
- Уточните сложные моменты

## ЭТАП 3: Анализ влияния на существующую систему

Цель: Определить, какие ИЗМЕНЕНИЯ потребуются в текущей архитектуре

### Анализ компонентных изменений

Для каждого затронутого компонента определите:

# Тип изменения
- Новый компонент нужно создавать?
- Существующий компонент нужно модифицировать?
- Существующий компонент нужно расширить с новым интерфейсом?
- Существующий компонент нужно оптимизировать?

# Какие функции изменяются
- Текущие функции/методы, которые нужно модифицировать
- Новые функции/методы, которые нужно добавить
- Какие функции нужно переделать полностью
- Какие функции нужно оптимизировать

# Какие интерфейсы изменяются
- Текущие API endpoints, которые меняются
- Новые endpoints, которые нужно создать
- Какие параметры добавляются/удаляются/меняют смысл
- Нужна ли версия нового API или можно развить текущую

### Анализ данных и хранилища

Для каждой сущности данных определите:

# Изменения в схеме
- Новые поля, которые нужно добавить
- Существующие поля, которые нужно изменить
- Новые отношения между сущностями
- Новые constraints или валидации

# Миграционные требования
- Нужна ли миграция существующих данных
- Как обработать состояние для старых данных
- Нужно ли поддерживать обе версии схемы временно
- Какой rollback план если миграция не удастся

# Индексы и оптимизации
- Какие новые индексы потребуются
- Нужно ли переиндексировать существующие данные
- Какие query patterns новые
- Какие query patterns изменятся

### Анализ интеграций и зависимостей

Определите:

# Новые интеграции
- С какими внешними сервисами нужна новая интеграция
- Какие API этих сервисов будут использоваться
- Какие версии API

# Изменения в существующих интеграциях
- Какие текущие интеграции затронуты
- Нужны ли изменения в параметрах вызовов
- Нужна ли обработка новых ответов

# Внутренние зависимости
- Какие компоненты система нужно скоординировать
- Какие изменения в текущих API требуются
- Нужна ли новая очередь сообщений, кэш, логирование

## ЭТАП 4: Определение требований

Цель: Четко определить ВСЕ функциональные и нефункциональные требования для этой функции

### Функциональные требования

Для каждой основной функциональности создайте запись:

# FR идентификатор и название
- Уникальный ID (FR-01, FR-02, etc.)
- Четкое название функции
- Категория (Core, Enhancement, Optional)

# Описание
- Что делает функция
- Кто её использует
- Когда она используется
- Почему она нужна

# Пользовательская история
- Как [роль], я хочу [действие], чтобы [выгода]

# Acceptance Criteria
- Что должно быть истинно после реализации
- Как будет валидирована функция
- Какие edge cases нужно обработать

# Связи
- Какие другие FR зависят от этой
- На какие существующие компоненты влияет

# Приоритет
- Критический (blockers, должно быть в MVP)
- Высокий (важно для MVP)
- Средний (хорошо иметь, но можно отложить)
- Низкий (nice-to-have)

### Нефункциональные требования

Для новой функции определите:

# Производительность
- Требуемое время отклика
- Пропускная способность
- Максимальное количество параллельных операций
- Требования к throughput

# Безопасность
- Какая авторизация требуется
- Какие данные чувствительны
- Какие атаки нужно защитить
- Требования к шифрованию

# Надежность
- Требуемый uptime
- Какие ошибки критичны
- Какой retry policy
- Механизмы graceful degradation

# Совместимость
- Какие браузеры/платформы нужно поддерживать
- Backward compatibility требования
- Какие версии dependencies

# Масштабируемость
- Как функция должна масштабироваться
- Какие bottlenecks потенциальные
- Какие оптимизации нужны заранее

## ЭТАП 5: Определение плана реализации

Цель: Разбить функциональность на реализуемые части

### Определение фаз реализации

# Phase 1: MVP / Minimum Viable Feature
- Что КРИТИЧНО для этой функции
- Что можно сделать в первый спринт
- Какие части кода нужно изменить

# Phase 2+: Расширения
- Какие nice-to-have части
- Когда их можно добавить
- Какие зависимости между фазами

### Определение модулей разработки

Для каждого модуля определите:

# Список файлов, которые нужно изменить
- В каких файлах нужны изменения
- Какой тип изменений (новый файл, модификация, удаление)
- Приблизительный объём изменений

# Точки интеграции
- Где новый код интегрируется с существующим
- Какие интерфейсы нужно согласовать
- Какие зависимости между модулями

# Тестовые точки
- Какие unit tests нужны
- Какие integration tests
- Какие E2E scenarios

### Определение рисков и mitigation

# Технические риски
- Какие сложные части требуют expertise
- Какие unknowns
- Какие constraints могут помешать
- Как минимизировать риск

# Операционные риски
- Какие зависимости от других команд
- Какие external dependencies
- Какие compliance требования
- Какой fallback plan

# Структура итогового FR документа

Feature Requirements документ ДОЛЖЕН содержать следующие 11 обязательных секций.

## Секция 1: Обзор функции

# Содержание
- Название функции и версия
- Краткое описание (2-3 предложения о том, что добавляется/изменяется)
- Тип изменения (New Feature, Enhancement, Bug Fix, Performance Optimization)
- Текущий статус (Planning, Design, In Development, Ready for Testing, Completed)
- Владелец функции и ключевые stakeholders
- Дата создания FR и версия базовой системы

# Формат
- Название: [проект] - [название функции]
- Версия FR: X.Y.Z
- Версия базовой системы: A.B.C (указать git commit или release tag)
- Тип: [New Feature / Enhancement / Bug Fix / Optimization]
- Статус: [текущая стадия]
- Владелец: [имя/роль]
- Stakeholders: [список ролей]

## Секция 2: Проблема и контекст

# Содержание
- Какую проблему решает функция (в текущей системе)
- Как текущая система справляется с этой проблемой
- Почему текущее решение недостаточно
- Какова бизнес-ценность изменения
- Контекст и предыстория (почему именно сейчас)

# Формат
- Текущее состояние: [описание текущего положения]
- Проблема: [конкретная проблема]
- Почему важно: [бизнес-обоснование]
- Целевое состояние: [как должно быть после реализации]

## Секция 3: Затронутые компоненты системы

# Содержание
- Список всех компонентов, которые будут изменены
- Тип изменения для каждого компонента
- Текущее назначение компонента
- Что именно изменится

# Формат
- Компонент A: [текущее назначение]
  - Тип изменения: [модификация / расширение / оптимизация]

# Протокол задавания уточняющих вопросов для FR

## Когда задавать вопросы

# Неоднозначная бизнес-логика
- Противоречивые требования от разных stakeholders
- Неясное поведение в edge cases
- Недокументированные бизнес-правила в коде

# Отсутствие информации о системе
- Не можете найти где хранятся данные
- Неясна текущая архитектура компонента
- Не ясны текущие constraints системы

# Неясные интеграции
- Как новая функция взаимодействует с существующим кодом
- Какие побочные эффекты могут быть
- Какие backward compatibility требования

# Риски и ограничения
- Какие technical constraints влияют на реализацию
- Какие compliance требования
- Какие performance implications

## Формат уточняющего вопроса

# Заголовок
❓ УТОЧНЯЮЩИЙ ВОПРОС [Секция FR] [Компонент если применимо]

# Контекст
- Что обнаружено в коде или что было сказано
- Где это обнаружено (файл, функция)
- Почему это важно

# Неоднозначность
- Что именно неясно
- Почему это вызывает неоднозначность
- Какие интерпретации возможны

# Возможные интерпретации
- A) Вариант 1 [описание и последствия]
- B) Вариант 2 [описание и последствия]
- C) Вариант 3 [описание и последствия]

# Вопрос
- Конкретный, закрытый вопрос
- Желательно требующий однозначного ответа

# Почему это критично
- Как неясность повлияет на реализацию
- Какие риски возникают
- Какие затраты времени это может добавить

# Лучшие практики написания FR

## Практика №1: Думайте о разработчике

Пишите FR так, как будто разработчик будет читать это БЕЗ доступа к исходному коду и БЕЗ возможности задать вопросы. Это означает:

# Включайте контекст
- Объясняйте ЧТО изменяется и ПОЧЕМУ
- Связывайте с существующей архитектурой
- Показывайте примеры

# Будьте явны
- Не предполагайте, что разработчик помнит весь код
- Выписывайте детали явно
- Включайте даже очевидное если это важно

# Будьте точны
- Используйте точные названия компонентов, функций, полей
- Указывайте файлы с номерами строк
- Показывайте примеры кода если сложно описать словами

## Практика №2: Определяйте приоритеты четко

Для каждого требования четко определите:

# Что ОБЯЗАТЕЛЬНО в MVP
- Какие функции критичны
- Какие acceptance criteria minimum

# Что можно отложить
- Nice-to-have функции
- Оптимизации
- Расширения

# Что может быть убрано
- Если дедлайн очень жесткий
- Какие части не критичны

## Практика №3: Документируйте решения

Для каждого архитектурного решения включайте:

# Что решили
- Конкретное решение или подход

# Почему это решение
- Какие альтернативы рассматривались
- Почему выбрано именно это
- Какие constraints это удовлетворяет

# Какие риски
- Какие потенциальные проблемы
- Как их митигировать

## Практика №4: Ссылайтесь на код

Всегда указывайте где в коде это уже сделано или нужно изменить:

# Используйте точные пути
- Относительные пути от корня проекта
- Номера строк если возможно
- Git commit хеши для исторического контекста

# Используйте точные имена
- Экспортируемые функции и классы
- Типы данных если используются
- Constants если есть

# Примеры
- Покажите как использовать API
- Покажите примеры データ
- Покажите примеры ошибок

# Финальные принципы работы с FR

# Принцип №1: Контекст архитектуры выше всего
FR создается НА ОСНОВЕ реального кода и существующей архитектуры. Каждое требование должно быть согласовано с реальностью системы, а не идеалом.

# Принцип №2: Минимум новой информации, максимум связи со старой
Не переписывайте архитектуру в FR если она не меняется. Ссылайтесь на существующую документацию. FR фокусируется на том, что МЕНЯЕТСЯ или ДОБАВЛЯЕТСЯ.

# Принцип №3: Трассируемость в коде
Каждое требование должно быть связано с конкретными местами в коде. Это позволяет разработчику быстро найти контекст.

# Принцип №4: Четкие приоритеты
Всегда четко разделяйте MVP от nice-to-have. Это позволяет команде решить что делать если сроки сжимаются.

# Принцип №5: Ясная интеграция
FR должна четко показывать как новая функция интегрируется с существующей системой. Какие компоненты меняются, какие нет.

# Принцип №6: Валидируемые критерии
Каждое требование должно иметь acceptance criteria, которые можно валидировать. Не субъективные и не требующие интерпретации.

# Принцип №7: Документ для действия
FR - это документ для ДЕЙСТВИЯ, а не для архивации. Каждый пункт должен быть полезен разработчику, тестировщику или DevOps.

# Заключение

Feature Requirements Document - это мост между идеей изменения и его реализацией. Хороший FR:

# Ясно передает ПОЧЕМУ нужно это изменение
- Бизнес-контекст понятен
- Проблема четко определена
- Ценность очевидна

# Четко описывает ЧТО нужно изменить
- Все затронутые компоненты идентифицированы
- Все требования явно описаны
- Все изменения трассируемы к коду

# Дает достаточно деталей КАК это делать
- Архитектурные решения обоснованы
- Интеграция с существующей системой ясна
- Миграционный путь четкий
- Риски идентифицированы

Используйте этот документ как руководство для систематического и полного определения требований для расширения вашей системы.
